## Overview

The GameData system allows plugins to access game internals through **signatures**, **offsets**, **addresses**, **patches**, and **vtables**. This enables hooking functions, reading memory, and modifying game behavior without hardcoded addresses.

GameData files are JSONC configuration files (JSON with comments) that contain platform-specific patterns and offsets. The system picks the entry for the current platform (Windows/Linux) and finds functions by signature scanning instead of hardcoded addresses, so most game updates need only a gamedata edit.

::callout{type="info"}
**Key Benefits:**
- Platform-independent code (Windows/Linux handled automatically)
- Resilient to game updates (signatures auto-locate addresses)
- Centralized configuration for memory operations
- Automatic binary patching support
::

## API Approaches

The s2sdk provides two ways to work with gamedata:

1. **Functional API** - Manual id management with `LoadGameConfigFile` / `CloseGameConfigFile`
2. **Object-Oriented API** - RAII wrapper using the `GameConfig` class (automatic cleanup)

::callout{type="info"}
**Recommended:** Use the **GameConfig class** for automatic resource management (RAII). It closes the gamedata config when the object is destroyed or closed.
::

## Loading and Closing GameData Files (Functional API)

Use `LoadGameConfigFile` to load a custom gamedata file and `CloseGameConfigFile` when done. `LoadGameConfigFile` returns a config id (`ConfigId`, an unsigned 32-bit integer); `0` means the load failed, and the reason is printed to the server console as `Could not load config: [paths] - <error>`.

::callout{type="info"}
**Path Array:** `LoadGameConfigFile` takes an **array of absolute file paths**. Every file that exists is read and merged in array order; files that do not exist are skipped, but at least one must exist. Build the paths from your plugin's location and the Plugify `configs` and `data` folders.

**Where to keep the file:** name it after your plugin, `<name>.gamedata.jsonc`, and pass three paths in this order: the plugin folder (the file from your package), `configs/<name>/` (edits of the server owner) and `data/<name>/`. A later file overrides the top-level keys of an earlier one, and files that do not exist are skipped. This way a server owner can fix a signature after a game update without touching your package.

**Merge depth:** the override works on whole top-level values. Since all entries live under the game key (`csgo`), an override file must contain a full copy of that section, not just the changed entry.
::

## JSON Schema Structure

GameData files use JSONC format. The top-level key is the game (`csgo` for CS2); the five sections live inside it, and each entry holds a value per platform (`win64`, `linuxsteamrt64`). Here's the basic structure:

```json
{
  "csgo": {
    "Signatures": {
      "SignatureName": {
        "library": "server",
        "win64": "48 89 5C 24 ? 48 89 6C 24 ? 48 89 74 24 ? 57 41 56 41 57 48 83 EC 40",
        "linuxsteamrt64": "55 48 89 E5 41 57 41 56 41 55 41 54 53 48 83 EC 18"
      }
    },
    "Offsets": {
      "OffsetName": {
        "win64": 123,
        "linuxsteamrt64": 456
      }
    },
    "Addresses": {
      "AddressName": {
        "signature": "SignatureName",
        "win64": [
          {
            "read_offs32": 3
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 3
          }
        ]
      }
    },
    "Patches": {
      "PatchName": {
        "signature": "SignatureName",
        "win64": "EB",
        "linuxsteamrt64": "90 90"
      }
    },
    "VTables": {
      "VTableName": {
        "library": "server",
        "table": "CBaseEntity"
      }
    }
  }
}
```

::callout{type="warning"}
**Important:** Entries must sit under the game key (`csgo`); a file without it fails to load with `Game section not found`. Pass absolute paths to `LoadGameConfigFile`; build them from your plugin's location as shown above.
::

## Using GameConfig Class (Object-Oriented API)

The `GameConfig` class is a **RAII wrapper** that automatically manages gamedata resources. Its constructor calls `LoadGameConfigFile` with the same array of paths, and it calls `CloseGameConfigFile` when destroyed or closed.

::callout{type="success"}
**Benefits of GameConfig Class:**
- Automatic resource cleanup (RAII pattern)
- No manual `CloseGameConfigFile` needed
- Cleaner, more maintainable code
- Type-safe interface with member methods
::

### GameConfig Methods

The `GameConfig` class provides the following methods:
- `GetPatch(name)` - Get the patch bytes (string) of a named patch
- `GetOffset(name)` - Get a named offset value
- `GetAddress(name)` - Get a resolved address
- `GetVTable(name)` - Get address of a virtual table
- `GetSignature(name)` - Get address of a named signature

It also has the usual handle helpers: a validity check (`IsValid` in C#, `operator bool` in C++, `Valid()` in Go, `valid()` in Python, JavaScript and Lua) and `close` / `Dispose` / `reset`.

::tabs{variant="card"}
::div{label="c#" icon="vscode-icons:file-type-csharp2"}
```csharp
using System.IO;
using Plugify;
using s2sdk;
using static s2sdk.s2sdk;

public class Sample : Plugin
{
    private GameConfig? gameConfig;

    public void OnPluginStart()
    {
        // Constructor automatically loads gamedata
        string file = $"{Name}.gamedata.jsonc";
        gameConfig = new GameConfig(new[]
        {
            Path.Combine(Location, file),
            Path.Combine(ConfigsDir, Name, file),
            Path.Combine(DataDir, Name, file),
        });

        if (!gameConfig.IsValid)
        {
            PrintToServer("Failed to load gamedata file!\n");
            return;
        }

        // Use member methods directly on the object
        int offset = gameConfig.GetOffset("SomeOffset");
        PrintToServer($"Offset value: {offset}\n");

        nint signature = gameConfig.GetSignature("SignatureName");
        PrintToServer($"Signature at: 0x{signature:X}\n");

        nint address = gameConfig.GetAddress("AddressName");
        PrintToServer($"Address at: 0x{address:X}\n");
    }

    public void OnPluginEnd()
    {
        // Dispose closes the gamedata config
        gameConfig?.Dispose();
        gameConfig = null;
    }
}
```

## Signatures

Signatures are byte patterns used to locate functions or data in game binaries. They're resilient to minor game updates.

### Signature Format

Signatures use hex bytes with `?` as wildcards:
- `48 89 5C 24` - Exact bytes
- `?` or `??` - Any single byte (wildcard)
- Space-separated hex values

`library` is the module to scan (`server`, `engine2`, `tier0`, ...). A pattern must match exactly once in that module. Instead of a pattern for a platform, an entry can also list `refs` (`{ "string": "..." }`, `{ "cvar": "..." }`, `{ "vtable": "..." }`; a `!` after the key excludes a match): they are used when there is no pattern for that platform or the pattern finds nothing.

### Generating Signatures

You can generate signatures using:

1. **IDA Pro** with [sigmaker plugin](https://github.com/ajkhoury/SigMaker-x64)
2. **Binary Ninja** with signature generation scripts
3. **Ghidra** with custom scripts

::callout{type="info"}
**Signature Naming:** If a signature starts with `@` (e.g., `@FunctionName`), the system will treat it as a **symbol name** instead of a byte pattern. This is useful for exported functions.
::

## Offsets

Offsets are numeric values representing memory positions or structure field offsets, or virtual function indices. They're platform-specific.

### Defining Offsets

```json
{
  "csgo": {
    "Offsets": {
      "HealthOffset": {
        "win64": 3216,
        "linuxsteamrt64": 3240
      },
      "VelocityOffset": {
        "win64": 1024,
        "linuxsteamrt64": 1040
      }
    }
  }
}
```

## Addresses

Addresses start from a base and apply a chain of steps to locate specific memory positions. The base is one of `signature` (a Signatures entry), `address` (another Addresses entry) or `vtable` (a VTables entry). Four step types are supported:

### Address Types

1. **`offset`** - Add N to the current address
2. **`read`** - Read the pointer stored at current address + N (one dereference)
3. **`read_offs32`** - Read the 32-bit relative offset stored at current address + N and compute the absolute address (`cur + N + 4 + offs32`)
4. **`index`** - Read the pointer at index N of a table (current address + N * 8), for example a virtual function from a vtable

### Defining Addresses

Addresses are defined as **arrays of action steps** for each platform:

```json
{
  "csgo": {
    "Addresses": {
      "GlobalVars": {
        "signature": "GlobalVarsSignature",
        "win64": [
          {
            "offset": 3
          }
        ],
        "linuxsteamrt64": [
          {
            "offset": 3
          }
        ]
      },
      "EntityList": {
        "signature": "EntityListSignature",
        "win64": [
          {
            "read_offs32": 10
          },
          {
            "read": 0
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 8
          },
          {
            "read": 0
          }
        ]
      },
      "SomeVirtualFunction": {
        "vtable": "CBaseEntity",
        "win64": [
          {
            "index": 111
          }
        ],
        "linuxsteamrt64": [
          {
            "index": 110
          }
        ]
      }
    }
  }
}
```

::callout{type="info"}
**Step Execution:** Each address action is executed sequentially. For example, `EntityList` first resolves the RIP-relative operand at offset 10 of the signature, then reads the pointer stored there.
::

## Patches

Patches allow automatic modification of game binaries at runtime. They locate code using signatures and replace bytes.

::callout{type="danger"}
**Warning:** Patches modify game memory directly. Incorrect patches can crash the server. Always verify bytes before patching!
::

### Defining Patches

Patches reference a base (a Signatures, Addresses or VTables entry) and specify the bytes to write at that address:

```json
{
  "csgo": {
    "Patches": {
      "VScriptEnable": {
        "signature": "VScriptInitialization",
        "win64": "BE 02",
        "linuxsteamrt64": "83 FE 02"
      },
      "NoValidation": {
        "address": "ValidationCheck",
        "win64": "EB",
        "linuxsteamrt64": "90 90"
      }
    }
  }
}
```

- **`signature`** / **`address`** / **`vtable`** - Name of the Signatures, Addresses or VTables entry whose address is patched
- **`win64` / `linuxsteamrt64`** - Hex bytes to write (patch bytes)

::callout{type="warning"}
**Caution:** Patches modify game memory directly and are automatically applied on load. Test thoroughly to avoid crashes!
::

::callout{type="info"}
**Automatic Application:** Patches are applied when the gamedata file is loaded and the original bytes are restored when the config is closed. You don't need to call any functions!
::

## VTables

Virtual tables (VTables) are used for virtual function lookups in C++ objects. Use them to find function pointers in class vtables.

```json
      "CBaseEntity": {
        "library": "server",
        "table": "CBaseEntity"
      },
      "CServerSideClient": {
        "library": "engine2",
```

## Method Reference

### File Management
| Method | Description |
|--------|-------------|
| `LoadGameConfigFile(paths)` | Load and merge gamedata files from an array of absolute paths. Returns a config id, or `0` on failure. Loading the same set of paths again returns the same id. |
| `CloseGameConfigFile(id)` | Close a config loaded by this plugin (restores its patches when the last user closes it). |

### Signatures
| Method | Description |
|--------|-------------|
| `GetGameConfigSignature(id, name)` | Get address of a named signature from specific config (null if not found). |
| `GetGameConfigSignatureAll(name)` | Search all loaded configs for signature. |

### Offsets
| Method | Description |
|--------|-------------|
| `GetGameConfigOffset(id, name)` | Get a named offset value from specific config (`-1` if not found). |
| `GetGameConfigOffsetAll(name)` | Search all loaded configs for offset. |

### Addresses
| Method | Description |
|--------|-------------|
| `GetGameConfigAddress(id, name)` | Get a resolved address from specific config (null if not found). |
| `GetGameConfigAddressAll(name)` | Search all loaded configs for address. |

### Patches
| Method | Description |
|--------|-------------|
| `GetGameConfigPatch(id, name)` | Get the patch bytes (hex string) of a named patch from specific config (empty if not found). |
| `GetGameConfigPatchAll(name)` | Search all loaded configs for patch. |

::callout{type="info"}
**Note:** Patches are automatically applied when loading gamedata. `GetGameConfigPatch()` only returns the configured bytes; it does not apply anything.
::

### VTables
| Method | Description |
|--------|-------------|
| `GetGameConfigVTable(id, name)` | Get address of a virtual table from specific config (null if not found). |
| `GetGameConfigVTableAll(name)` | Search all loaded configs for vtable. |

::callout{type="info"}
**`*All` functions** scan every loaded config, including s2sdk's own gamedata, and return the value from the first config that has the entry. Use them to read s2sdk's entries (its config id is not handed out), and keep your entry names unique so they do not collide with other configs.
::

## Tips and Best Practices

1. **Always close gamedata files** - Use `CloseGameConfigFile()` in `OnPluginEnd()` (or close the `GameConfig` object)
2. **Validate signatures** - Check if returned addresses are not null before using them
3. **Use meaningful names** - Name your signatures, offsets, and addresses descriptively
4. **Document your patterns** - Comment where signatures came from and what they point to (JSONC allows comments)
5. **Test on all platforms** - Ensure both Windows and Linux patterns are correct
6. **Keep gamedata updated** - Update signatures when game updates break them
7. **Keep patches minimal** - Patch only the bytes you need; they are written as is at the base address
8. **Cache addresses** - Store resolved addresses instead of calling Get methods repeatedly
9. **Organize your JSON** - Group related signatures, offsets, and addresses together
10. **Version your gamedata** - Consider adding version comments to track changes

## Troubleshooting

### Signature Not Found
- **Cause**: Pattern doesn't match game binary (the console shows `Failed to resolve signature '<name>': ...`)
- **Solution**: Regenerate signature using IDA/Binary Ninja, check platform-specific patterns

### Patch Not Applied
- **Cause**: The base of the patch did not resolve (the console shows `Failed to apply patch '<name>': ...`)
- **Solution**: Fix the signature, address or vtable the patch points to, then update the patch bytes for the new game version

### Invalid Address Returned
- **Cause**: Signature failed or offset calculation incorrect
- **Solution**: Verify signature works, check `offset`, `read`, `read_offs32` and `index` values

### Gamedata File Not Loading
- **Cause**: No file exists at any of the paths, invalid JSON, or no `csgo` section (the console shows `Could not load config: [paths] - <error>`)
- **Solution**: Check that the paths are absolute, validate JSON syntax, and wrap the sections in `"csgo": { ... }`

::callout{type="warning"}
**Platform Differences:** Always test your gamedata on both Windows and Linux. Signatures and offsets often differ between platforms!
::

## Advanced Topics

### Symbol-Based Signatures

For exported functions, use `@` prefix to reference by symbol name:

```json
{
  "csgo": {
    "Signatures": {
      "CreateInterface": {
        "library": "server",
        "win64": "@CreateInterface",
        "linuxsteamrt64": "@CreateInterface"
      }
    }
  }
}
```

### Multi-Level Address Resolution

Chain several `read` steps to follow pointer chains:

```json
{
  "csgo": {
    "Addresses": {
      "DeepPointer": {
        "signature": "BaseSignature",
        "win64": [
          {
            "read_offs32": 10
          },
          {
            "read": 0
          },
          {
            "read": 16
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 8
          },
          {
            "read": 0
          },
          {
            "read": 16
          }
        ]
      }
    }
  }
}
```

This first resolves the RIP-relative address of a global, reads the pointer stored in it, then reads the pointer stored 16 bytes into that object. Each `read` step is one dereference.

### Relative Offset Addresses (read_offs32)

Use `read_offs32` for RIP-relative addressing (common in x64). This reads a 32-bit relative offset and calculates the absolute address:

```json
{
  "csgo": {
    "Addresses": {
      "v8::Isolate::Enter": {
        "signature": "CSScript::ResolveModule",
        "win64": [
          {
            "read_offs32": 57
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 38
          }
        ]
      }
    }
  }
}
```

This is useful when the signature points to instructions like `call [rip + offset]` or `lea reg, [rip + offset]`. The value of `read_offs32` is the byte offset where the 32-bit relative offset is located; the result is that position + 4 + the stored offset.
