## Обзор

Система GameData позволяет плагинам получать доступ к внутренним компонентам игры через **сигнатуры**, **смещения**, **адреса**, **патчи** и **виртуальные таблицы**. Это позволяет перехватывать функции, читать память и изменять поведение игры без жёстко закодированных адресов.

Файлы GameData - это конфигурационные файлы JSONC (JSON с комментариями), которые содержат платформозависимые шаблоны и смещения. Система выбирает запись для текущей платформы (Windows/Linux) и находит функции сканированием сигнатур вместо жёстко закодированных адресов, поэтому после большинства обновлений игры достаточно поправить gamedata.

::callout{type="info"}
**Ключевые преимущества:**
- Платформонезависимый код (Windows/Linux обрабатываются автоматически)
- Устойчивость к обновлениям игры (сигнатуры автоматически находят адреса)
- Централизованная конфигурация для операций с памятью
- Автоматическая поддержка бинарных патчей
::

## Подходы к API

s2sdk предоставляет два способа работы с gamedata:

1. **Функциональный API** - Ручное управление id конфигурации с помощью `LoadGameConfigFile` / `CloseGameConfigFile`
2. **Объектно-ориентированный API** - RAII-обёртка с использованием класса `GameConfig` (автоматическая очистка)

::callout{type="info"}
**Рекомендуется:** Используйте **класс GameConfig** для автоматического управления ресурсами (RAII). Он закрывает конфигурацию gamedata при уничтожении или закрытии объекта.
::

## Загрузка и закрытие файлов GameData (функциональный API)

Используйте `LoadGameConfigFile` для загрузки пользовательского файла gamedata и `CloseGameConfigFile` по завершении. `LoadGameConfigFile` возвращает id конфигурации (`ConfigId`, беззнаковое 32-битное число); `0` означает, что загрузка не удалась, а причина выводится в консоль сервера как `Could not load config: [paths] - <error>`.

::callout{type="info"}
**Массив путей:** `LoadGameConfigFile` принимает **массив абсолютных путей к файлам**. Каждый существующий файл читается и сливается в порядке массива; несуществующие файлы пропускаются, но хотя бы один должен существовать. Стройте пути от расположения плагина и папок Plugify `configs` и `data`.

**Где хранить файл:** называйте его по имени плагина, `<name>.gamedata.jsonc`, и передавайте три пути в таком порядке: папка плагина (файл из вашего пакета), `configs/<name>/` (правки владельца сервера) и `data/<name>/`. Более поздний файл перекрывает ключи верхнего уровня более раннего, а несуществующие файлы пропускаются. Так владелец сервера может исправить сигнатуру после обновления игры, не трогая ваш пакет.

**Глубина слияния:** перекрытие работает целыми значениями верхнего уровня. Все записи лежат под ключом игры (`csgo`), поэтому файл-перекрытие должен содержать полную копию этого раздела, а не только изменённую запись.
::

### Получение расположения плагина

Каждый язык предоставляет способ доступа к директории плагина и папкам Plugify `configs` и `data`:

| Язык | Папка плагина | Папки `configs` / `data` | Имя плагина |
|----------|---------------|----------------------------|-------------|
| C# | `Location` | `ConfigsDir` / `DataDir` | `Name` |
| C++ | `GetLocation()` | `plg::GetConfigsDir()` / `plg::GetDataDir()` | `GetName()` |
| Python | `self.location` | `self.configs_dir` / `self.data_dir` | `self.name` |
| Go | `plugin.Location()` (`plugin` - значение, возвращённое `plugify.NewPlugin`) | `plugify.ConfigsDir()` / `plugify.DataDir()` | `plugin.Name()` |
| JavaScript | `this.location` | `this.configs_dir` / `this.data_dir` | `this.name` |
| Lua | `self.location` | `self.configs_dir` / `self.data_dir` | `self.name` |

::tabs{variant="card"}

```csharp
using System.IO;
using Plugify;
using s2sdk;
using static s2sdk.s2sdk;

public class Sample : Plugin
{
    private uint gameData;

    public void OnPluginStart()
    {
        // <plugin folder> -> configs/<name>/ -> data/<name>/
        string file = $"{Name}.gamedata.jsonc";
        string[] paths =
        {
            Path.Combine(Location, file),
            Path.Combine(ConfigsDir, Name, file),
            Path.Combine(DataDir, Name, file),
        };

        // Load gamedata file (requires array of paths)
        gameData = LoadGameConfigFile(paths);

        if (gameData == 0)
        {
            PrintToServer("Failed to load gamedata file!\n");
            return;
        }

        // Use gamedata methods...
        int offset = GetGameConfigOffset(gameData, "SomeOffset");
        PrintToServer($"Offset value: {offset}\n");
    }

    public void OnPluginEnd()
    {
        // Clean up gamedata
        if (gameData != 0)
        {
            CloseGameConfigFile(gameData);
            gameData = 0;
        }
    }
}
```

## Структура схемы JSON

Файлы GameData используют формат JSONC. Ключ верхнего уровня - игра (`csgo` для CS2); пять разделов лежат внутри него, и каждая запись содержит значение для каждой платформы (`win64`, `linuxsteamrt64`). Вот базовая структура:

```json
{
  "csgo": {
    "Signatures": {
      "SignatureName": {
        "library": "server",
        "win64": "48 89 5C 24 ? 48 89 6C 24 ? 48 89 74 24 ? 57 41 56 41 57 48 83 EC 40",
        "linuxsteamrt64": "55 48 89 E5 41 57 41 56 41 55 41 54 53 48 83 EC 18"
      }
    },
    "Offsets": {
      "OffsetName": {
        "win64": 123,
        "linuxsteamrt64": 456
      }
    },
    "Addresses": {
      "AddressName": {
        "signature": "SignatureName",
        "win64": [
          {
            "read_offs32": 3
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 3
          }
        ]
      }
    },
    "Patches": {
      "PatchName": {
        "signature": "SignatureName",
        "win64": "EB",
        "linuxsteamrt64": "90 90"
      }
    },
    "VTables": {
      "VTableName": {
        "library": "server",
        "table": "CBaseEntity"
      }
    }
  }
}
```

::callout{type="warning"}
**Важно:** Записи должны лежать под ключом игры (`csgo`); файл без него не загрузится с ошибкой `Game section not found`. Передавайте в `LoadGameConfigFile` абсолютные пути; стройте их от расположения плагина, как показано выше.
::

## Использование класса GameConfig (объектно-ориентированный API)

Класс `GameConfig` - это **RAII-обёртка**, которая автоматически управляет ресурсами gamedata. Его конструктор вызывает `LoadGameConfigFile` с тем же массивом путей, а при уничтожении или закрытии объект вызывает `CloseGameConfigFile`.

::callout{type="success"}
**Преимущества класса GameConfig:**
- Автоматическая очистка ресурсов (паттерн RAII)
- Не требуется ручной вызов `CloseGameConfigFile`
- Более чистый и поддерживаемый код
- Типобезопасный интерфейс с методами-членами
::

### Методы GameConfig

Класс `GameConfig` предоставляет следующие методы:
- `GetPatch(name)` - Получить байты (строку) именованного патча
- `GetOffset(name)` - Получить значение именованного смещения
- `GetAddress(name)` - Получить разрешённый адрес
- `GetVTable(name)` - Получить адрес виртуальной таблицы
- `GetSignature(name)` - Получить адрес именованной сигнатуры

Также у него есть обычные методы для работы с дескриптором: проверка валидности (`IsValid` в C#, `operator bool` в C++, `Valid()` в Go, `valid()` в Python, JavaScript и Lua) и `close` / `Dispose` / `reset`.

::tabs{variant="card"}
::div{label="c#" icon="vscode-icons:file-type-csharp2"}
```csharp
using System.IO;
using Plugify;
using s2sdk;
using static s2sdk.s2sdk;

public class Sample : Plugin
{
    private GameConfig? gameConfig;

    public void OnPluginStart()
    {
        // Constructor automatically loads gamedata
        string file = $"{Name}.gamedata.jsonc";
        gameConfig = new GameConfig(new[]
        {
            Path.Combine(Location, file),
            Path.Combine(ConfigsDir, Name, file),
            Path.Combine(DataDir, Name, file),
        });

        if (!gameConfig.IsValid)
        {
            PrintToServer("Failed to load gamedata file!\n");
            return;
        }

        // Use member methods directly on the object
        int offset = gameConfig.GetOffset("SomeOffset");
        PrintToServer($"Offset value: {offset}\n");

        nint signature = gameConfig.GetSignature("SignatureName");
        PrintToServer($"Signature at: 0x{signature:X}\n");

        nint address = gameConfig.GetAddress("AddressName");
        PrintToServer($"Address at: 0x{address:X}\n");
    }

    public void OnPluginEnd()
    {
        // Dispose closes the gamedata config
        gameConfig?.Dispose();
        gameConfig = null;
    }
}
```

## Сигнатуры

Сигнатуры - это байтовые шаблоны, используемые для поиска функций или данных в игровых бинарных файлах. Они устойчивы к незначительным обновлениям игры.

### Формат сигнатуры

Сигнатуры используют шестнадцатеричные байты с `?` в качестве подстановочных знаков:
- `48 89 5C 24` - Точные байты
- `?` или `??` - Любой одиночный байт (подстановочный знак)
- Шестнадцатеричные значения, разделённые пробелами

`library` - модуль, в котором идёт поиск (`server`, `engine2`, `tier0`, ...). Шаблон должен совпадать в этом модуле ровно один раз. Вместо шаблона для платформы запись может содержать `refs` (`{ "string": "..." }`, `{ "cvar": "..." }`, `{ "vtable": "..." }`; `!` после ключа исключает совпадение): они используются, когда для платформы нет шаблона или шаблон ничего не нашёл.

### Генерация сигнатур

Вы можете генерировать сигнатуры с помощью:

1. **IDA Pro** с плагином [sigmaker](https://github.com/ajkhoury/SigMaker-x64)
2. **Binary Ninja** со скриптами генерации сигнатур
3. **Ghidra** с пользовательскими скриптами

::callout{type="info"}
**Именование сигнатур:** Если сигнатура начинается с `@` (например, `@FunctionName`), система будет обрабатывать её как **имя символа** вместо байтового шаблона. Это полезно для экспортируемых функций.

## Адреса

Адреса начинаются от базы и применяют цепочку шагов для определения конкретных позиций в памяти. База - одно из: `signature` (запись Signatures), `address` (другая запись Addresses) или `vtable` (запись VTables). Поддерживаются четыре типа шагов:

### Типы адресов

1. **`offset`** - Прибавить N к текущему адресу
2. **`read`** - Прочитать указатель, хранящийся по адресу текущий + N (одно разыменование)
3. **`read_offs32`** - Прочитать 32-битное относительное смещение по адресу текущий + N и вычислить абсолютный адрес (`cur + N + 4 + offs32`)
4. **`index`** - Прочитать указатель с индексом N из таблицы (текущий адрес + N * 8), например виртуальную функцию из vtable

### Определение адресов

Адреса определяются как **массивы шагов действий** для каждой платформы:

```json
{
  "csgo": {
    "Addresses": {
      "GlobalVars": {
        "signature": "GlobalVarsSignature",
        "win64": [
          {
            "offset": 3
          }
        ],
        "linuxsteamrt64": [
          {
            "offset": 3
          }
        ]
      },
      "EntityList": {
        "signature": "EntityListSignature",
        "win64": [
          {
            "read_offs32": 10
          },
          {
            "read": 0
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 8
          },
          {
            "read": 0
          }
        ]
      },
      "SomeVirtualFunction": {
        "vtable": "CBaseEntity",
        "win64": [
          {
            "index": 111
          }
        ],
        "linuxsteamrt64": [
          {
            "index": 110
          }
        ]
      }
    }
  }
}
```

::callout{type="info"}
**Выполнение шагов:** Каждое действие адреса выполняется последовательно. Например, `EntityList` сначала разрешает RIP-относительный операнд по смещению 10 от сигнатуры, затем читает хранящийся там указатель.

## Патчи

Патчи позволяют автоматически изменять игровые бинарные файлы во время выполнения. Они находят код с помощью сигнатур и заменяют байты.

::callout{type="danger"}
**Предупреждение:** Патчи напрямую изменяют память игры. Неправильные патчи могут привести к сбою сервера. Всегда проверяйте байты перед применением патчей!
::

### Определение патчей

Патчи ссылаются на базу (запись Signatures, Addresses или VTables) и указывают байты, которые записываются по этому адресу:

```json
{
  "csgo": {
    "Patches": {
      "VScriptEnable": {
        "signature": "VScriptInitialization",
        "win64": "BE 02",
        "linuxsteamrt64": "83 FE 02"
      },
      "NoValidation": {
        "address": "ValidationCheck",
        "win64": "EB",
        "linuxsteamrt64": "90 90"
      }
    }
  }
}
```

- **`signature`** / **`address`** / **`vtable`** - Имя записи Signatures, Addresses или VTables, адрес которой патчится
- **`win64` / `linuxsteamrt64`** - Шестнадцатеричные байты для записи (байты патча)

::callout{type="warning"}
**Осторожно:** Патчи напрямую изменяют память игры и применяются автоматически при загрузке. Тщательно тестируйте, чтобы избежать сбоев!
::

::callout{type="info"}
**Автоматическое применение:** Патчи применяются при загрузке файла gamedata, а исходные байты восстанавливаются при закрытии конфигурации. Вызывать какие-либо функции не нужно!
::

## Виртуальные таблицы

Виртуальные таблицы (VTables) используются для поиска виртуальных функций в объектах C++. Используйте их для поиска указателей на функции в виртуальных таблицах классов.

### Определение виртуальных таблиц

Запись VTables указывает модуль (`library`) и класс, чью виртуальную таблицу нужно найти (`table`). Таблица ищется по имени RTTI, поэтому одна запись работает на обеих платформах:

```json
{
  "csgo": {
    "VTables": {
      "CBaseEntity": {
        "library": "server",
        "table": "CBaseEntity"
      },
      "CServerSideClient": {
        "library": "engine2",
        "table": "CServerSideClient"
      }
    }
  }
}
```

## Справочник методов

### Управление файлами
| Метод | Описание |
|--------|-------------|
| `LoadGameConfigFile(paths)` | Загрузить и слить файлы gamedata из массива абсолютных путей. Возвращает id конфигурации или `0` при ошибке. Повторная загрузка того же набора путей возвращает тот же id. |
| `CloseGameConfigFile(id)` | Закрыть конфигурацию, загруженную этим плагином (патчи восстанавливаются, когда её закрывает последний пользователь). |

### Сигнатуры
| Метод | Описание |
|--------|-------------|
| `GetGameConfigSignature(id, name)` | Получить адрес именованной сигнатуры из конкретной конфигурации (null, если не найдена). |
| `GetGameConfigSignatureAll(name)` | Искать сигнатуру во всех загруженных конфигурациях. |

### Смещения
| Метод | Описание |
|--------|-------------|
| `GetGameConfigOffset(id, name)` | Получить значение именованного смещения из конкретной конфигурации (`-1`, если не найдено). |
| `GetGameConfigOffsetAll(name)` | Искать смещение во всех загруженных конфигурациях. |

### Адреса
| Метод | Описание |
|--------|-------------|
| `GetGameConfigAddress(id, name)` | Получить разрешённый адрес из конкретной конфигурации (null, если не найден). |
| `GetGameConfigAddressAll(name)` | Искать адрес во всех загруженных конфигурациях. |

### Патчи
| Метод | Описание |
|--------|-------------|
| `GetGameConfigPatch(id, name)` | Получить байты (hex-строку) именованного патча из конкретной конфигурации (пустая строка, если не найден). |
| `GetGameConfigPatchAll(name)` | Искать патч во всех загруженных конфигурациях. |

::callout{type="info"}
**Примечание:** Патчи применяются автоматически при загрузке gamedata. `GetGameConfigPatch()` только возвращает заданные байты и ничего не применяет.
::

### Виртуальные таблицы
| Метод | Описание |
|--------|-------------|
| `GetGameConfigVTable(id, name)` | Получить адрес виртуальной таблицы из конкретной конфигурации (null, если не найдена). |
| `GetGameConfigVTableAll(name)` | Искать виртуальную таблицу во всех загруженных конфигурациях. |

::callout{type="info"}
**Функции `*All`** просматривают все загруженные конфигурации, включая собственный gamedata s2sdk, и возвращают значение из первой конфигурации, где есть запись. Используйте их, чтобы читать записи s2sdk (id его конфигурации не выдаётся), и давайте своим записям уникальные имена, чтобы они не пересекались с другими конфигурациями.
::

## Советы и лучшие практики

1. **Всегда закрывайте файлы gamedata** - Используйте `CloseGameConfigFile()` в `OnPluginEnd()` (или закрывайте объект `GameConfig`)
2. **Проверяйте сигнатуры** - Проверяйте, что возвращённые адреса не равны null перед их использованием
3. **Используйте осмысленные имена** - Давайте описательные имена вашим сигнатурам, смещениям и адресам
4. **Документируйте ваши шаблоны** - Комментируйте, откуда взялись сигнатуры и на что они указывают (JSONC допускает комментарии)
5. **Тестируйте на всех платформах** - Убедитесь, что шаблоны для Windows и Linux верны
6. **Держите gamedata в актуальном состоянии** - Обновляйте сигнатуры, когда обновления игры их ломают
7. **Делайте патчи минимальными** - Патчите только нужные байты; они записываются как есть по адресу базы
8. **Кешируйте адреса** - Сохраняйте разрешённые адреса вместо повторного вызова методов Get
9. **Организуйте ваш JSON** - Группируйте связанные сигнатуры, смещения и адреса вместе
10. **Версионируйте ваш gamedata** - Рассмотрите возможность добавления комментариев с версиями для отслеживания изменений

## Устранение неполадок

### Сигнатура не найдена
- **Причина**: Шаблон не соответствует игровому бинарному файлу (в консоли `Failed to resolve signature '<name>': ...`)
- **Решение**: Перегенерируйте сигнатуру, используя IDA/Binary Ninja, проверьте платформозависимые шаблоны

### Патч не применён
- **Причина**: База патча не разрешилась (в консоли `Failed to apply patch '<name>': ...`)
- **Решение**: Исправьте сигнатуру, адрес или виртуальную таблицу, на которую указывает патч, затем обновите байты патча для новой версии игры

### Возвращён недействительный адрес
- **Причина**: Сигнатура не сработала или вычисление смещения неверно
- **Решение**: Проверьте работу сигнатуры, проверьте значения `offset`, `read`, `read_offs32` и `index`

### Файл gamedata не загружается
- **Причина**: Ни по одному из путей нет файла, недействительный JSON или нет раздела `csgo` (в консоли `Could not load config: [paths] - <error>`)
- **Решение**: Проверьте, что пути абсолютные, валидируйте синтаксис JSON и оберните разделы в `"csgo": { ... }`

::callout{type="warning"}
**Различия платформ:** Всегда тестируйте ваши gamedata на Windows и Linux. Сигнатуры и смещения часто различаются между платформами!
::

## Продвинутые темы

### Сигнатуры на основе символов

Для экспортируемых функций используйте префикс `@` для ссылки по имени символа:

```json
{
  "csgo": {
    "Signatures": {
      "CreateInterface": {
        "library": "server",
        "win64": "@CreateInterface",
        "linuxsteamrt64": "@CreateInterface"
      }
    }
  }
}
```

### Многоуровневое разрешение адресов

Объединяйте несколько шагов `read`, чтобы следовать цепочкам указателей:

```json
{
  "csgo": {
    "Addresses": {
      "DeepPointer": {
        "signature": "BaseSignature",
        "win64": [
          {
            "read_offs32": 10
          },
          {
            "read": 0
          },
          {
            "read": 16
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 8
          },
          {
            "read": 0
          },
          {
            "read": 16
          }
        ]
      }
    }
  }
}
```

Сначала разрешается RIP-относительный адрес глобальной переменной, затем читается хранящийся в ней указатель, затем указатель, хранящийся на 16 байт дальше внутри этого объекта. Каждый шаг `read` - одно разыменование.

### Адреса с относительным смещением (read_offs32)

Используйте `read_offs32` для RIP-относительной адресации (распространено в x64). Это читает 32-битное относительное смещение и вычисляет абсолютный адрес:

```json
{
  "csgo": {
    "Addresses": {
      "v8::Isolate::Enter": {
        "signature": "CSScript::ResolveModule",
        "win64": [
          {
            "read_offs32": 57
          }
        ],
        "linuxsteamrt64": [
          {
            "read_offs32": 38
          }
        ]
      }
    }
  }
}
```

Это полезно, когда сигнатура указывает на инструкции вроде `call [rip + offset]` или `lea reg, [rip + offset]`. Значение `read_offs32` - это байтовое смещение, где находится 32-битное относительное смещение; результат равен этой позиции + 4 + сохранённое смещение.
